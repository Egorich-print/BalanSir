# M3.7 Post-Implementation Audit

Date: after `cbaae13` (M3.7 committed). Scope: adversarial review of the
flow-level datapath, per the four audit areas. No architecture change was
introduced; findings are classified by proof class.

---

## Audit 1 — RemoveRule / Rollback

### 1.1 Partial-failure rollback (normal path): correct

`DaemonExecutorAdapter::execute` (`adapters.rs:52-100`) applies each
`UpdatePolicy`/`RemovePolicy` op and counts succeeded/failed. If any op fails
(`report.success == false`), the coordinator runs `rollback_and_fail`
(`coordinator.rs:211-229`) → `DaemonRollback::rollback` (`adapters.rs:194-224`):

1. computes `to_revert` = live-ActualState rule ids not in the pre-execution
   snapshot;
2. calls `executor.remove_rule(id)` for each (M3.7 handle-based nft removal);
3. restores ActualState from the snapshot.

**Finding (FACT):** In the normal partial-failure path, kernel rules added by
the failed execution are removed by id, and ActualState is restored. No orphan
is left. Covered by `rollback_reverts_added_rules_and_restores_snapshot`
(`adapters.rs` tests).

### 1.2 Executor drop between Apply and ack: orphaned kernel rule (real gap)

`apply_rule` (`adapters.rs:112-141`) pushes to ActualState **only on
`ActionResult::Applied`**. If the executor applies the nft rule but the IPC ack
is lost (connection drop), `ExecutorClient::execute` returns `Failed`
(`executor_client.rs`), `apply_rule` returns Err → op counted failed → ActualState
is **not** updated.

Rollback then computes `to_revert` from ActualState, which lacks the rule that
the kernel actually has → the kernel rule is **orphaned**: present in nft, absent
from ActualState, and not reverted.

**Finding (FACT):** daemon↔executor ack-gap can orphan a kernel rule. The daemon's
reconnect model (ADR-013) re-reconciles `Desired − Actual`, but the orphan is
invisible to ActualState, so a later reconcile will not remove it.

**Classification:** real TOCTOU at the IPC boundary. **Not auto-fixed** — closing
it requires executor-side actual-state enumeration or ack-gap reconciliation
(architecture decision, not an M3.7 defect). Recorded for a hardening milestone.

### 1.3 RemoveRule semantics (M3.7)

`MsgType::RemoveRule` decodes a `u32` rule id (`service.rs:271-276`), the
`NftablesExecutor` resolves `balansir:<id>` → nft handle (`nft -a list chain`)
and deletes precisely (`nftables.rs:147-180`). Idempotent when absent. The
daemon only updates ActualState on success (`adapters.rs:66-86`). **Not
flush-all.**

**Finding (FACT):** RemoveRule is handle-based, deterministic, and failure is
surfaced.

## Audit 2 — IPv4 / IPv6

### 2.1 Addressing is IPv4-only

`ActionRequest.src_ip/dst_ip` are `[u8;4]` (`types.rs:338-339`). The executor's
nft render never emits `ip6 saddr`. The table family is `inet` (dual-stack), so
IPv6 packets would reach the chain, but there is **no IPv6 match expression** and
no IPv6 address representation.

### 2.2 The current datapath is chain-level, not flow-level

`DaemonExecutorAdapter::apply_rule` sends **all-zero flow fields**
(`adapters.rs:115-120`: `src_ip=[0;4]`, `dst_port=0`, `protocol=0`, ...).
Consequently `to_nft_spec`/`to_mark_spec` emit rules with **no
proto/cidr/dport/mark match** — e.g. `nft add rule inet balansir forward drop`
(a whole-chain verdict), not `... ip saddr X th dport Y drop`.

**Root cause (FACT):** `DesiredRule` (`types.rs:402-407`) carries only
`{id, action, priority}` — **no matcher** (verified in the M3.7 spike). The
planner diff produces `UpdatePolicy(DesiredRule)`, so flow criteria cannot reach
the executor.

**Finding:** "flow-level datapath v0" is strictly **chain-level verdict**
enforcement today. It is honest (ADR-014: M3.7 enforces what
`DesiredRule`/`ActionRequest` can express), but the audit must state plainly:
**there is no per-flow classification yet.** Per-flow rules require a
matcher-carrying desired-rule operation (a later contract decision).

### 2.3 IPv6 is not "hidden in Unsupported"

`Action::Route`/`Forward`/`Shape` are `Unsupported` (explicit), but IPv6 is
**not** reported `Unsupported` — it is simply unrepresentable (IPv4-only address
type). This matches ADR-014's "IPv6 deferred" without an explicit rejection
path.

**Finding (FACT + INFERENCE):** IPv6 enforcement is absent by type limitation,
not by an explicit datapath decision. Deferred per ADR-014; no hidden
silent-allow claim.

## Audit 3 — Fail-open / Fail-closed

| Failure | Observed behavior (FACT) | Semantic |
|---|---|---|
| Executor down / IPC lost | `ExecutorClient` returns Err → `apply_rule`/`RemovePolicy` fail → reconcile fails → rollback; new policy **not** applied; **existing kernel rules persist** (no flush-all) | delta fail-closed, existing policy persists |
| Daemon crash | nft rules already installed remain in the kernel (kernel state persists) | last-applied policy persists |
| Apply failure | op counted failed → reconcile fails → rollback; no fabricated `Applied` | fail-closed on the delta |
| nft/ip binary absent | executor `NftablesBackend::new`/`add_rule` fail → `Failed` | observable, not silent |

**Finding (FACT):** the datapath has no explicit fail-open/fail-closed product
policy; behavior is "apply what the daemon commands, keep last-applied kernel
state on failure." This is consistent with ADR-013/014 and the mission's
"reconcile, not replay," and matches the earlier decision not to hardcode
STRICT semantics until product profiles exist. **No defect.**

**Note (INFERENCE):** because the daemon's startup `DesiredState` is empty
(`main.rs:62`), no enforcement rules are installed until a config source is
wired. The chain exists and is contract-tested; it is not yet driven by real
desired state in production.

## Conclusions

1. **RemoveRule / rollback** are architecturally correct for the normal path;
   the ack-gap orphan is a real but recorded limitation (not auto-fixed; needs
   executor-side actual-state reconciliation).
2. **IPv4/IPv6**: the datapath is IPv4-addressed; more importantly it is
   **chain-level verdict** (no per-flow classification) because `DesiredRule`
   has no matcher — honest but must be stated. IPv6 is deferred by type
   limitation, not hidden.
3. **Fail-open/fail-closed**: no product semantic is hardcoded; behavior is
   "keep last-applied kernel state, fail-closed on the delta." Consistent with
   ADR-013/014. No defect.
4. **Real enforcement** is **proved by tests** (contract) and **provable by
   privileged environment** (existing `#[ignore]` netns tests); it is **not yet
   proved** for the full daemon→executor→kernel path with real desired state.

## What was not changed
No code was modified during this audit. The gaps above (ack-gap orphan, per-flow
matcher, IPv6, product fail-open/closed) are recorded as boundaries requiring
separate decisions, not auto-fixed — consistent with the mission's STOP rules.
